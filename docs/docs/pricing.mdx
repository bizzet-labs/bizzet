# Pricing

## 何を解くか

店は同じ商品でも、客が払う通貨・タイミング・条件によって最終的な金額を変えたいと考えます。通貨の換算だけでなく、数量や時間帯、買った記録の証明といった条件を満たすと変わる価格を、鍵を持たない決済チャネルではなく1箇所（Checkout コントラクト）で判定します。

## 境界 — 決済チャネルとビジネス向けウォレット

| | 決済チャネル（値札 / EC 購入ボタン） | ビジネス向けウォレット（金庫） |
| --- | --- | --- |
| 置く場所 | 店頭の値札、または EC サイトの購入ボタン | 拠点・サイト1つに1つ |
| 権限 | 鍵を持たず、表示・読み取り・`Paid` の購読だけ | 資金に触れる唯一の場所（出金は複数承認） |
| 最初に作ること | 値札1台（レート表示、切替、QR / NFC、「済」表示） | 受取、値札ごとの売上紐づけ、2承認の出金、仕訳（CSV） |
| 既存で代替できるか | 値札は新規、EC ボタンは既存の決済 UI で代替可 | N Suite や Safe で代替可（差し替え可能にしておく） |

## 仕組み — 決済の流れ

客のウォレットが値札の QR か NFC を読んで JPYC か USDC で払い、共通の Checkout コントラクトが受け取る通貨と違えば Uniswap で交換して `Paid` イベントを発行し、[ビジネス向けウォレット](./wallet.mdx)の法人アカウントが選んだ通貨（JPYC か USDC）で受け取ります。値札は鍵を持たず `Paid` イベントを直接見て「済」に切り替わり、POS 端末・店員・決済代行はこの経路に存在しません。

決済チャネルが端点、ビジネス向けウォレットが金庫です。客と事業者は別の通貨を見ていますが、交換はコントラクトの中で1回で終わるため、どちらも為替を意識しません。決済チャネルは鍵を持たない低権限の入口で、「支払われた」をサーバーではなくチェーンのイベントから直接知ることで、検証をオフチェーンのハブに戻す型を避けています。値札を例にしていますが、EC の購入ボタンも同じ `pay(itemId)` を呼ぶだけで、右側のウォレット以降は変わりません。

## 仕組み — 条件つき価格

| 条件の種類 | 判定材料 | 判定の場所 |
| --- | --- | --- |
| 数量 | 決済時のカート内容 | Checkout コントラクト |
| 時間帯 | ブロックのタイムスタンプ | Checkout コントラクト |
| 買った記録 | レシートの検証コントラクトが返す真偽値 | 検証コントラクト（レシート側） |

条件はすべて店が事前に登録したものだけを使い、決済チャネル自身は判断しません。チャネルは鍵を持たないため、判断させると端末の改ざんに弱くなります。

## 設計の選択

| 設計の選択 | 採る | 採らない |
| --- | --- | --- |
| 表示レートの出所 | 実行と同じ Uniswap の JPYC/USDC プール（操作に強い平均価格を出すオラクルフックを経由） | Chainlink の JPY/USD フィード（法定通貨の為替で、JPYC/USDC の価格と一致しない） |
| 実行レートの出所 | Uniswap のプール | 表示レートをそのまま実行に使う |
| 割引の判定場所 | Checkout コントラクト（決済と同じトランザクション） | 決済チャネル（鍵を持たず改ざんに弱い） |
| 見積の有効期限 | 短い期限を必須にする | 期限なし（レート変動を見積が拾えない） |
| 決済チャネルの鍵 | 持たせない（署名する場面を設計から消す） | 持たせる（端末を盗まれたら資金に届く） |
| 受取先の設定 | ENS（`shop.eth` のテキストレコード）に受取通貨とウォレットのアドレスを置く | チャネルごとに埋め込む（差し替えのたびに全チャネルを直す） |
| 値札のパネル | 白黒の e-ink（部分書き換え約0.3秒） | 3色以上の e-ink（書き換えに10秒以上） |
| 「済」を出す時点 | `Paid` を含むブロックが出た時点 | 最終確定まで待つ（Ethereum では約13分） |

交換に使う JPYC/USDC のプールには、店頭決済の金額を吸収できる流動性がある前提とします。今後は、Bizzet 自身がこのプールに流動性を提供する予定です。
