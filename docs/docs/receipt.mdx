# Receipt

Receipt は、客が何を買ったかを、店ではなく客の手元に残す仕組みです。店は「条件を満たすか」を問うことしかできず、購買履歴そのものを持ちません。このページは、Receipt が何を解き、bizzet の決済とどこで接するかをまとめます。レシートの見せ方、客のウォレットへの載せ方、証明の作り方の細部は Receipt の別プロジェクトが決めるため、ここでは扱いません。

## 何を解くか

店は「前に買ってくれた客にだけ割引する」「同じ商品を3回買ったら特典を付ける」といった、買った記録にもとづく値付けをしたいと考えます。これまでは会員カードや顧客データベースで購買履歴を店が持つ必要があり、その管理の手間と漏えいのおそれを店が負い、客は自分の買い物を店に集められることを受け入れるしかありませんでした。Receipt は記録を客の手元に置き、店には条件を満たすかどうかの答えだけを渡すことで、店が購買履歴を持たずに済むようにします。

## 考え方

- **記録を持つのは客。** 支払いのときに記録が客の手元に残り、店のサーバーには何も残りません。
- **店が知るのは真偽だけ。** 店は「この条件を満たすか」を問い、どの支払いか・いつ・どのアドレスからかは知りません。
- **支払いと証明をつなげない。** 客は支払ったアドレスとは別のアドレスから証明できるため、証明から過去の支払いをたどれません。
- **同じ記録で同じ特典を何度も使わせない。** 特典ごとに一度しか使えない印を残し、店のデータベースを使わずに二重利用を防ぎます。

## できること

| 機能 | 何ができるか | 使う人 |
| --- | --- | --- |
| レシートの受け取り | 支払いと同時の、客の手元への記録の保存 | 客 |
| 条件の証明 | どの支払いかを明かさない、「この店でこの商品を買った」ことの証明 | 客 |
| 条件の判定 | 証明の検証と、真偽の返却 | Checkout コントラクト |
| 二重利用の防止 | 特典ごとの、同じ記録の使用済みの記録 | 検証コントラクト |

## bizzet との境界

### bizzet が渡すもの

Checkout コントラクトは、支払いを受け付けるときに、客が支払いに添えたレシートの識別子（コミットメント）を、店と商品ごとの集合に登録します。識別子は客の秘密から作られた値で、それだけでは誰の記録かも、どの支払いかも分かりません。客が識別子を添えなければ登録はせず、支払いはそのまま通ります。

### bizzet が受け取るもの

条件つき価格の「買った記録」の判定で、Checkout コントラクトは次の3つを検証コントラクトに渡し、真偽を受け取ります。

| 渡すもの | 中身 |
| --- | --- |
| 条件 | 店と商品の組（どの集合に入っているかを問うか） |
| 特典の範囲 | 二重利用を防ぐ単位（例：この店のこのキャンペーン） |
| 証明 | 客が作った、集合に入っていることのゼロ知識証明 |

真偽が真で、その特典の範囲でまだ使われていなければ、Checkout は割引を適用して同じ取引の中で使用済みを記録します。

### bizzet が扱わないもの

レシートの画面での見せ方、客のウォレットが秘密をどう持つか、証明の作り方と標準化は、Receipt の別プロジェクトの範囲です。bizzet の側は、識別子の登録と、真偽を返す検証の呼び出しだけを持ちます。

## 仕組み

1. 客が値札の QR か NFC から支払うとき、客のウォレットがレシートの識別子を支払いに添える
2. Checkout コントラクトは支払いを受け付け、識別子を店と商品ごとの集合に登録する
3. 次に買うとき、客は支払ったアドレスとは別のアドレスでもよく、手元の秘密から「その集合に入っている」ことのゼロ知識証明を作り、支払いに添える
4. Checkout コントラクトは検証コントラクトに証明を渡し、真なら割引した金額で決済し、その特典の範囲での使用済みを記録する

店が集合に入っている客の一覧を見ても分かるのは識別子の並びだけで、どの識別子が誰の証明に使われたかは分かりません。

## 設計の選択

| 設計の選択 | 採る | 採らない |
| --- | --- | --- |
| 記録の置き方 | ゼロ知識の集合への識別子の登録（Semaphore v4 のグループ） | 客のアドレスへの NFT やアテステーション（誰が何を買ったかが公開される） |
| 証明の単位 | 店と商品ごとの集合に入っていること | 支払いの取引そのものの提示（過去の支払いをたどれる） |
| 二重利用の防止 | 特典の範囲ごとの nullifier | 店のデータベースでの使用済みの管理 |
| 判定の場所 | Checkout コントラクト（決済と同じ取引） | 値札や購入ボタン（鍵を持たず改ざんに弱い） |
| 証明を出すアドレス | 支払いと別のアドレスも可 | 支払いと同じアドレスに限定 |

ゼロ知識の集合には Semaphore v4 を使います。Semaphore v4 は、集合に入っていることと、同じ範囲で二度使っていないことを、誰の記録かを明かさずに示せる仕組みです。PSE による v4.0.0 の監査を受け、証明に使う公開パラメータは 2024年7月に400人以上が参加したトラステッドセットアップで作られています。Ethereum・Sepolia・Polygon・Arbitrum などに同じアドレスで配置済みのため、bizzet はコントラクトを書かずに使えます（Semaphore の公式ドキュメント、2026年9月27日確認）。

## 守れないこと

支払いそのものは公開のチェーンに残るため、どのアドレスがいつどの店に支払ったかは、レシートとは関係なく誰でも見られます。Receipt が隠すのは、あとの証明と過去の支払いのつながりで、支払いの事実ではありません。支払いの事実まで隠す必要が出た場合は、支払いの仕組みの側で扱います。

## 決まっていないこと

- **ベータ版での扱い**：ベータ版では Receipt を作らず、条件つき価格の「買った記録」も使いません。最初に作るのは値札1台の基本の流れのためです。
- **期間の条件**：仮置き。「30日以内に買った」のような期間つきの条件は、期間ごとに集合を分けるか、証明に日付の範囲を含めるかを決めた時点で更新します。
- **登録のガス代**：仮置き。識別子の登録は支払いと同じ取引で行うため、今は支払う客のガス代に含まれる前提です。Paymaster で肩代わりするかを決めた時点で更新します。
- **客の秘密の保管**：客のウォレットが秘密をどう持ち、端末を替えたときにどう移すかは、Receipt の別プロジェクトが決めます。
