# ウォレットの設計

ウォレットを動かす仕組みの設計をまとめます。対象は、資金を保管する Safe と、その承認・権限・自動ブリッジに関わるコントラクト、およびそれらを使うためにチェーンの外に置く仕組みです。支払いを受け付ける Checkout コントラクトと値札は Pricing の範囲、ダッシュボードとインデクサーは画面側の範囲のため、ここでは扱いません。

## 全体の構成

ウォレットは、メンバーの端末・チェーンの外の仕組み・Sepolia 上のコントラクトの3層で動きます。メンバーが端末で署名した取引は、バンドラーが EntryPoint へ送り、Safe4337Module を通して Safe で実行されます。

## コントラクトの構成

### Bizzet が配置するもの

| コントラクト | 配置の単位 | 役割 | バージョン・監査 |
| --- | --- | --- | --- |
| Safe | シングルトンはチェーンに1つ、プロキシはグループに1つ | 資金の保管と、オーナー・しきい値の管理 | v1.4.1 |
| Zodiac Roles v2 | 自動ブリッジの送り元になる Safe に1つ | キーパーに、宛先を固定した送金だけを許可する | v2（G0 Group・Omniscia 監査） |
| Safe のパスキー署名者 | ファクトリはチェーンに1つ、署名者はメンバーに1つ | メンバーのパスキーを Safe のオーナーとして扱う | v0.2.1（Certora・Nethermind・Hats 監査） |
| Safe4337Module | チェーンに1つ、各 Safe で有効化 | ERC-4337 経由の署名送信と、ガス代の肩代わりの受け口 | v0.3.0（Ackee・Certora・Nethermind 監査） |

いずれも監査を受けたコミットのまま配置し、コードは変更しません。

### Solidity のバージョン

どのコントラクトも、監査を受けたときのコンパイラ設定に合わせて固定します。バージョンや最適化の設定を変えるとバイトコードが変わり、監査の対象外になるためです。

| コントラクト | Solidity | 最適化の runs | EVM バージョン | viaIR |
| --- | --- | --- | --- | --- |
| Safe v1.4.1 | 0.7.6 | 仮置き：公式の配置と同じ設定 | 仮置き：公式の配置と同じ設定 | なし |
| Zodiac Roles v2 | 0.8.21 | 100 | shanghai（0.8.21 の既定） | なし |
| Safe のパスキー署名者 v0.2.1 | 0.8.26 | 10,000,000 | paris | あり（FCL の P-256 検証だけなし） |
| Safe4337Module v0.3.0 | 0.8.23 | 10,000,000 | paris | なし |

Safe v1.4.1 のリポジトリは、最適化の設定を環境変数で渡す作りで、設定ファイルに値がありません。仮置き：公式に配置されたバイトコードと一致する設定を確認した時点で更新します。

ウォレットの範囲に、Bizzet が自分で書くコントラクトはありません。コンパイラは、上の4つをそれぞれのリポジトリの設定のまま使います。

### Bizzet が配置せずに使うもの

| コントラクト | 役割 | 備考 |
| --- | --- | --- |
| EntryPoint v0.7 | ERC-4337 の取引の入り口 | Safe4337Module v0.3.0 が対応する版 |
| Paymaster | ガス代の肩代わり | 提供元は「外部のサービスを使うもの」で扱う |
| CCTP v2（TokenMessenger） | チェーン間の USDC の移動 | 自動ブリッジの送り先を本部の Safe に固定して呼ぶ |
| Uniswap v4 PoolManager | JPYC で受け取るときの USDC からの交換 | ホームチェーンにだけある |
| P-256 の署名検証（RIP-7212） | パスキー署名の検証 | Sepolia は対応済み。ないチェーンでは検証コントラクトで代替 |

## オフチェーンの構成

### 外部のサービスを使うもの

| 仕組み | 役割 | 提供元 |
| --- | --- | --- |
| バンドラー | 端末で署名した取引をまとめ、EntryPoint へ送る | 仮置き：Pimlico |
| Paymaster | ガス代の肩代わりと、肩代わりする取引の判定 | 仮置き：Pimlico |
| キーパー | 閾値か1日1回で、Roles v2 を通して Sweep を起動 | 仮置き：Gelato Web3 Functions |

仮置き：提供元は、ベータ版で使う料金と Sepolia での動作を確かめた時点で確定します。端末は EntryPoint を直接呼ばず、必ずバンドラーを通します。キーパーは Bizzet 専用の送信元アドレスを持ち、そのアドレスに Roles v2 のロールを与えるため、Bizzet は鍵を管理せず、Solidity も書かずに済みます。

### Bizzet のバックエンドが持つもの

バックエンドは独立したサーバーを立てず、画面と同じ SvelteKit のサーバー側の処理として動かし、データは Neon（Postgres）に置いて Drizzle で扱います。仮置き：置き場所は Vercel とし、ベータ版で使う料金を確かめた時点で確定します。

| 役割 | バックエンドに置く理由 |
| --- | --- |
| パスキーと署名者の対応表 | ログイン時の WebAuthn の応答に公開鍵が含まれず、登録時に保存しておく必要があるため |
| 2人承認の途中の署名 | 1人目の署名を、2人目が署名するまで保管する場所がオンチェーンにないため |
| 閲覧権限と招待 | Viewer はオンチェーンに何も持たず、見られる範囲をオンチェーンで判定できないため |
| Paymaster の API キー | ブラウザに置くと、誰でもガス代の肩代わりを使えてしまうため |

仮置き：2人承認の途中の署名は、自前で保管するか Safe の Transaction Service を使うかを、まだ決めていません。

## デプロイの構造

<DeploymentDiagram />

- ホームチェーン（Sepolia）に、本部の Safe と店舗の Safe を置く
- 本部の Safe が上位にあり、各店舗の Safe のオーナーの1人になる
- 本部の Safe のしきい値は 2（2人承認）。仮置き：店舗の Safe のしきい値は、まだ決めていません
- 客が払うチェーン（Fuji・Amoy）にも、着金を受ける Safe と Roles v2 を置く。仮置き：この Safe を店舗ごとに置くか、チェーンに1つにするかは、まだ決めていません

## 本部の Safe の数

本部の Safe は、1つの組織に1つだけ置きます。設計上は複数置くこともできますが、運用の負荷を下げるために1つに絞ります。

| 観点 | 1つに絞る理由 |
| --- | --- |
| 資金の把握 | 店舗の Safe から本部の Safe への一方向の流れだけ見れば、残高の確認・監査・会計との突合が済む |
| 自動ブリッジ | キーパーに許可する送り先が1アドレスで済み、店舗を増やしても Roles v2 の設定を変えずに済む |
| 承認の運用 | 2人承認のオーナーの顔ぶれとしきい値を1か所で管理でき、オーナーの交代もオンチェーンの操作1回で済む |
| 障害時の対応 | 鍵の紛失や復旧の手順が1パターンで済む |

本部の Safe が複数あると、店舗ごとに「どの本部へ送るか」の設定と確認が増え、設定漏れや誤送金の元になります。予算の枠を分けたいだけなら、本部の Safe を増やさず、店舗の Safe（グループ）を増やして対応します。別の法人や会計の単位で資金を完全に分けたい場合は、組織を分けて、組織ごとに本部の Safe を1つ置きます。仮置き：組織を分ける仕組み（ダッシュボードのログイン先・メンバー・権限の分離）は、複数の組織を扱う要件が出た時点で決めます。

## 本部の Safe の作成

本部の Safe は、配置前にアドレスを確定し、最初の取引の中で配置します。

1. 本部の Owner と Approver が、ウォレットでパスキーを登録し、署名者を持つ
2. ダッシュボードで、それらの署名者をオーナーとする Safe のアドレスを CREATE2 で求め、本部のグループに保存する
3. 最初の取引の UserOperation に、Safe を配置する呼び出しを含めて送る。配置のガス代は Paymaster が肩代わりするため、事前に本部が資金を用意する必要はない

この方式は、配置だけの取引がなく、失敗したときの後始末も要らないため、運用の負荷が最も低くなります。一方で「アドレスは決まっているが、まだオンチェーンに存在しない」期間が生じるため、店舗の Safe のオーナーに加える前や、自動ブリッジの送り先に固定する前には、ダッシュボードで配置済みかを確認し、未配置なら自分自身への 0 ETH の送金を最初の取引として配置を済ませます。

本部の Safe のオーナーはパスキーの署名者のため、メールアドレスとパスワードでログインしたダッシュボードの Owner だけでは署名できません。アドレスの確定と配置の指示はダッシュボードで行い、配置の署名はウォレットで行います。配置後にオーナーを増やす場合は、アドレスが変わらないよう Safe のオーナー変更で行い、Safe を作り直しません。

仮置き：2人承認の Safe を UserOperation で扱うには、1人目の署名の保管先が必要です。保管先は「Bizzet のバックエンドが持つもの」で未決のため、決まった時点でこの手順を更新します。

## ロールの割り当て

| 役職 | 所属するグループ | ロール | オンチェーンでの姿 |
| --- | --- | --- | --- |
| 経営 | 本部 | Owner | 本部の Safe のオーナー |
| 会計部 | 本部 | Approver | 本部の Safe のオーナー |
| 店長 | 店舗 | Viewer | なし |
| スタッフ | 店舗 | Viewer | なし |

Owner と Approver は、パスキー署名者を所属するグループの Safe のオーナーとして加えます。Viewer はオンチェーンに何も持たず、パスキーはログインにだけ使います。

## 強制する場所

| 項目 | 強制する場所 |
| --- | --- |
| 出金の承認 | Safe 本体（オーナーであることと、しきい値） |
| 2人承認 | 本部の Safe のしきい値 2 |
| 権限の付与（メンバーの追加） | Safe 本体（オーナーの変更） |
| 残高の閲覧 | 画面側（オンチェーンでは強制しない） |
| Sweep の起動 | Roles v2（キーパーに、宛先を固定した関数だけを許可） |

仮置き：権限の付与は、権限管理では Owner 1人で行える前提ですが、Safe のオーナー変更はしきい値の承認が要るため、本部の Safe では Owner 1人では実行できません。どちらを優先するかを決めた時点で更新します。

## 自動ブリッジとの接点

客が払うチェーンの Safe に着金した USDC は、Roles v2 のロールを持つキーパーが CCTP v2 の TokenMessenger を呼んで、ホームチェーンの本部の Safe へ移します。Roles v2 はキーパーに、受け取り先を本部の Safe に固定した呼び出しだけを許可するため、キーパーの鍵が漏れても資金はほかへ送れません。起動は、外部のサービスのキーパーが行います。
