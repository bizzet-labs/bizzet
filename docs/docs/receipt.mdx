# Receipt

Receipt は、客が何を買ったかを、店ではなく客の手元に残す仕組みです。店は「条件を満たすか」を問うことしかできず、購買履歴そのものを持ちません。このページは、Receipt が何を解き、ベータ版でどこまで作り、bizzet の決済とどこで接するかをまとめます。

## 何を解くか

店は「前に買ってくれた客にだけ割引する」といった、買った記録にもとづく値付けをしたいと考えます。これまでは会員カードや顧客データベースで購買履歴を店が持つ必要があり、その管理の手間と漏えいのおそれを店が負い、客は自分の買い物を店に集められることを受け入れるしかありませんでした。Receipt は記録を客の手元に置き、店には条件を満たすかどうかの答えだけを渡すことで、店が購買履歴を持たずに済むようにします。

## 考え方

- **記録を持つのは客。** 支払いのときに記録が客の手元に残り、店のサーバーには何も残りません。
- **店が知るのは真偽だけ。** 店は「この条件を満たすか」を問い、どの支払いか・いつ・どのアドレスからかは知りません。
- **支払いと証明をつなげない。** 客は支払ったアドレスとは別のアドレスから証明できるため、証明から過去の支払いをたどれません。
- **同じ記録で同じ特典を何度も使わせない。** 特典ごとに一度しか使えない印を残し、店のデータベースを使わずに二重利用を防ぎます。
- **自前のコントラクトを増やさない。** 集合の管理と証明の検証は、監査済みで配置済みの Semaphore v4 に任せます。

## ベータ版の範囲

ベータ版の Receipt は、次の範囲に絞ります。

| 項目 | ベータ版の決め |
| --- | --- |
| 店と集合 | 店は1つ、集合は商品ごとに1つ |
| 特典 | 同じ商品を前に買った客に、1回だけ割引 |
| チェーン | Sepolia に配置済みの Semaphore v4 |
| 客側の作り | bizzet の決済ページが秘密を持ち、識別子と証明を作る |
| ガス代 | 登録も検証も、支払う客が払う（Sepolia のテスト ETH） |
| 割引の率の登録 | bizzet の運用者が、商品と価格と一緒に Checkout の管理用の関数で登録する |
| 秘密の引き継ぎ | しない。端末やブラウザを替えると、それまでのレシートは使えない |

割引の率を登録する画面は作りません。店が1つで値札も1台のため、登録は運用者が行えば足りるからです。Checkout の管理用の関数が変えられるのは商品・価格・割引の率だけで、資金には触れません。

## できること

| 機能 | 何ができるか | 行う主体 |
| --- | --- | --- |
| レシートの受け取り | 支払いと同時の、商品ごとの集合への識別子の登録 | 客（決済ページ） |
| 条件の証明 | どの支払いかを明かさない、「この商品を買った」ことの証明 | 客（決済ページ） |
| 条件の判定 | 証明の検証と、割引の適用 | Checkout コントラクト |
| 二重利用の防止 | 特典ごとの使用済みの記録 | Semaphore v4 |

## bizzet との境界

### 判定の呼び出し

Checkout コントラクトは、支払いに証明が添えられていたとき、次の3つを Semaphore v4 に渡して検証します。検証が通れば割引を適用し、通らなければ支払いそのものを失敗させます。

| 渡すもの | 中身 |
| --- | --- |
| 集合 | 商品ごとの集合の ID（どの商品を買ったことがあるかを問うか） |
| 特典の範囲 | 二重利用を防ぐ単位。ベータ版では集合の ID と同じ（商品ごとに1回） |
| 証明 | 客が作った、集合に入っていることのゼロ知識証明 |

### bizzet が扱わないもの

レシートの画面での見せ方、客が使うウォレットへの秘密の載せ方、証明の作り方の標準化は、ベータ版の範囲外です。ベータ版の bizzet は、決済ページでの秘密の保管と証明の作成、Checkout からの登録と検証の呼び出しだけを持ちます。

### 初めて買うとき

1. 客が値札の QR か NFC から bizzet の決済ページを開くと、決済ページが手元の秘密からその商品用の識別子を作り、支払いの中身に添える。客のウォレットはその取引に署名するだけで、秘密には触れない
2. Checkout コントラクトは支払いを受け付け、識別子を商品ごとの集合に登録する

### 2回目に買うとき

3. 決済ページは、集合の中身をチェーンから読んで「その集合に入っている」ことのゼロ知識証明をブラウザで作り、支払いに添える。支払うアドレスは前回と別でもよい
4. Checkout コントラクトは証明を Semaphore v4 に渡し、真なら割引した金額で決済する。使用済みの印は同じ取引の中で記録される

店が集合の中身を見ても分かるのは識別子の並びだけで、どの識別子が誰の証明に使われたかは分かりません。

## 識別子と証明の決め

- **識別子は商品ごとに作る。** 元の秘密1つから、店と商品ごとに別の識別子を決まった手順で作ります。同じ識別子を複数の集合に登録すると、公開の集合を突き合わせるだけで商品をまたいで購入がつながるためです。
- **証明は支払うアドレスに縛る。** 証明には支払うアドレスを含めて作り、Checkout はそのアドレスからの支払いにだけ証明を認めます。チェーンに出た証明を第三者が自分の支払いに載せ、割引と使用済みの印を横取りできないようにするためです。
- **同じ集合には再登録しない。** すでに入っている商品の支払いには識別子を添えず、証明だけを添えます。同じ識別子を重ねて登録しても意味がなく、ガス代が増えるだけのためです。
- **証明は1時間以内に使う。** 集合は支払いのたびに更新され、古い集合をもとに作った証明は更新から1時間だけ通ります。決済ページは支払いの直前に証明を作り、1時間を過ぎたら作り直します。
- **秘密はブラウザに置く。** 決済ページが秘密をブラウザに保存します。端末やブラウザを替えると秘密が失われ、それまでのレシートは使えなくなります。

## 設計の選択

| 設計の選択 | 採る | 採らない |
| --- | --- | --- |
| 記録の置き方 | ゼロ知識の集合への識別子の登録（Semaphore v4 のグループ） | 客のアドレスへの NFT やアテステーション（誰が何を買ったかが公開される） |
| 証明の単位 | 商品ごとの集合に入っていること | 支払いの取引そのものの提示（過去の支払いをたどれる） |
| 二重利用の防止 | 特典の範囲ごとの nullifier | 店のデータベースでの使用済みの管理 |
| 検証の場所 | Checkout から呼ぶ Semaphore v4 本体（決済と同じ取引） | bizzet 自前の検証コントラクト（監査のない Solidity が増える） |
| 秘密の置き場所 | bizzet の決済ページのブラウザ保存 | 客のウォレットの中（一般のウォレットに秘密を持つ機能がない） |
| 証明を出すアドレス | 支払いと別のアドレスも可 | 支払いと同じアドレスに限定 |

ゼロ知識の集合には Semaphore v4 を使います。Semaphore v4 は、集合に入っていることと、同じ範囲で二度使っていないことを、誰の記録かを明かさずに示せる仕組みです。集合は誰でも作れ、作った側だけが登録でき、検証は使用済みの印を本体の中に記録します。PSE による v4.0.0 の監査を受け、証明に使う公開パラメータは 2024年7月に400人以上が参加したトラステッドセットアップで作られています。Ethereum・Sepolia・Polygon・Arbitrum などに同じアドレスで配置済みのため、bizzet は Checkout から呼ぶだけで使えます（Semaphore の公式ドキュメントとコントラクトのソース、2026年9月27日確認）。

## 守れないこと

- **支払いの事実。** 支払いそのものは公開のチェーンに残るため、どのアドレスがいつどの店に支払ったかは、レシートとは関係なく誰でも見られます。Receipt が隠すのは、あとの証明と過去の支払いのつながりです。
- **集合が小さいときの匿名性。** 識別子は支払いと同じ取引で登録されるため、識別子と支払ったアドレスのつながりは公開です。証明が隠すのは「集合のどの識別子か」だけなので、集合に客が1人しかいなければ誰の証明かは分かります。ベータ版は客が少なく集合も小さいため、匿名性は弱い前提で扱います。

## ベータ版で扱わないもの

| 扱わないもの | 理由 |
| --- | --- |
| 回数の条件（3回買ったら）と期間の条件（30日以内に買ったら） | 集合に入っていることの証明では、回数も期間も表せないため |
| 割引の率を店が登録する画面 | 店が1つで、運用者の登録で足りるため |
| ガス代の肩代わり | Sepolia のテスト ETH で足り、本番の費用はベータ版の計測を見て本番の設計で決めるため |
| 端末を替えても使える秘密 | バックアップやウォレットの署名から秘密を作る仕組みが要り、最小構成を超えるため |
| 複数の店と、店をまたぐ特典 | ベータ版の店は1つのため |
