# ウォレットの設計

ウォレットを動かす仕組みの設計をまとめます。対象は、資金を保管する Safe と、その承認・権限・自動ブリッジに関わるコントラクト、それらを使うためにチェーンの外に置く仕組み、およびメンバーの登録から出金までの流れです。支払いを受け付ける Checkout コントラクトと値札は Pricing の範囲、ダッシュボードとインデクサーは画面側の範囲のため、ここでは扱いません。

## 全体の構成

ウォレットは、メンバーの端末・チェーンの外の仕組み・Sepolia 上のコントラクトの3層で動きます。メンバーは端末のパスキーで Safe の取引に署名するだけで、チェーンへの送信は bizzet の中継用アカウントが ERC-4337 の取引として行い、ガス代は Paymaster が肩代わりします。

## コントラクトの構成

### bizzet が配置するもの

| コントラクト | 配置の単位 | 役割 | バージョン・監査 |
| --- | --- | --- | --- |
| Safe | シングルトンはチェーンに1つ、プロキシはグループに1つと中継用に1つ | 資金の保管と、オーナー・しきい値の管理 | v1.4.1 |
| Zodiac Roles v2 | 店舗の Safe と、自動ブリッジの送り元になる Safe に1つ | キーパーに、本部の Safe への送金だけを許可する | v2（G0 Group・Omniscia 監査） |
| Safe のパスキー署名者 | ファクトリはチェーンに1つ、署名者は Owner と Approver に1つ | メンバーのパスキーを Safe のオーナーとして扱う | v0.2.1（Certora・Nethermind・Hats 監査） |
| Safe4337Module | チェーンに1つ、中継用アカウントで有効化 | ERC-4337 経由の署名送信と、ガス代の肩代わりの受け口 | v0.3.0（Ackee・Certora・Nethermind 監査） |

いずれも監査を受けたコミットのまま配置し、コードは変更しません。グループの Safe には Safe4337Module を入れず、fallback handler には CompatibilityFallbackHandler を置きます。本部の Safe が店舗の Safe の取引に署名するときの ERC-1271 の検証に使うためです。

### Solidity のバージョン

どのコントラクトも、監査を受けたときのコンパイラ設定に合わせて固定します。バージョンや最適化の設定を変えるとバイトコードが変わり、監査の対象外になるためです。

| コントラクト | Solidity | 最適化 | EVM バージョン | viaIR |
| --- | --- | --- | --- | --- |
| Safe v1.4.1 | 0.7.6 | なし | istanbul | なし |
| Zodiac Roles v2 | 0.8.21 | runs 100 | shanghai（0.8.21 の既定） | なし |
| Safe のパスキー署名者 v0.2.1 | 0.8.26 | runs 10,000,000 | paris | あり（FCL の P-256 検証だけなし） |
| Safe4337Module v0.3.0 | 0.8.23 | runs 10,000,000 | paris | なし |

Safe v1.4.1 の設定は、Sepolia に配置された SafeL2 の検証済みソース（Blockscout、2026年9月27日確認）に合わせています。ウォレットの範囲に bizzet が自分で書くコントラクトはなく、コンパイラは上の4つをそれぞれのリポジトリの設定のまま使います。

### bizzet が配置せずに使うもの

| コントラクト | 役割 | 備考 |
| --- | --- | --- |
| EntryPoint v0.7 | ERC-4337 の取引の入り口 | Safe4337Module v0.3.0 が対応する版 |
| Paymaster | ガス代の肩代わり | 提供元は「外部のサービスを使うもの」で扱う |
| CCTP v2（TokenMessenger） | チェーン間の USDC の移動 | 自動ブリッジの送り先を本部の Safe に固定して呼ぶ |
| Uniswap v4 PoolManager | JPYC で受け取るときの USDC からの交換 | ホームチェーンにだけある |
| P-256 の署名検証（RIP-7212） | パスキー署名の検証 | Sepolia は対応済み。ないチェーンでは検証コントラクトで代替 |

## オフチェーンの構成

### 外部のサービスを使うもの

| 仕組み | 役割 | 提供元 | 料金 |
| --- | --- | --- | --- |
| バンドラー | 中継用アカウントの取引をまとめ、EntryPoint へ送る | Pimlico | テストネットは無料、本番はガス代に10%上乗せ |
| Paymaster | 中継用アカウントの取引のガス代の肩代わり | Pimlico | バンドラーと同じ |
| キーパー | 閾値か1日1回で、Roles v2 を通して Sweep を起動 | Gelato Web3 Functions | テストネットは無料、本番は前払い残高から |

料金は各社の公開ページ（2026年9月27日確認）によります。端末はバンドラーを呼ばず、中継用アカウントだけが呼びます。キーパーは bizzet 専用の送信元アドレスを持ち、そのアドレスに Roles v2 のロールを与えるため、bizzet は鍵を管理せず、Solidity も書かずに済みます。

### bizzet のバックエンドが持つもの

バックエンドは独立したサーバーを立てず、画面と同じ SvelteKit のサーバー側の処理として動かし、データは Neon（Postgres）に置いて Drizzle で扱います。仮置き：置き場所は Vercel とし、商用利用に要る Pro プランの料金を確かめた時点で確定します。

| 役割 | バックエンドに置く理由 |
| --- | --- |
| パスキーと署名者の対応表 | ログイン時の WebAuthn の応答に公開鍵が含まれず、登録時に保存しておく必要があるため |
| 出金の申請と途中の署名 | 1人目の署名を、2人目が署名するまで保管する場所がオンチェーンにないため |
| 閲覧権限と招待 | Viewer はオンチェーンに何も持たず、見られる範囲をオンチェーンで判定できないため |
| グループの Safe のアドレスと作成時の設定 | 画面ごとに計算し直すと設定の食い違いで別のアドレスになるため |
| 中継用アカウントの鍵 | 署名がそろった取引をチェーンへ送る主体が要るため |

出金の申請と途中の署名は、Safe の Transaction Service に頼らず自前で保管します。画面とインデクサーを bizzet が持ち、Safe 公式のサービスに依存しない方針にそろえるためです。

### 中継用アカウント

中継用アカウントは、bizzet のバックエンドの鍵1つをオーナーとする Safe（しきい値 1）で、Safe4337Module を有効にして ERC-4337 の取引を送れるようにしたものです。資金は持たず、次の2つだけを行います。

- グループの Safe とパスキー署名者の配置
- 署名がそろったグループの Safe の取引（`execTransaction`）の実行

メンバーの署名は Safe の取引そのものに対して行い、中継用アカウントの取引には含めません。Paymaster の肩代わりの承認は10分で切れるため、1人目と2人目の署名の間が空く2人承認では、同じ ERC-4337 の取引を2人で署名する形が成り立たないからです。中継用アカウントの鍵はデプロイ先の環境変数に置き、Paymaster の肩代わりはこのアカウントの取引だけを対象にします。鍵が漏れても、オーナーの署名がない取引は Safe が拒むため、グループの資金は動かせません。

## データの持ち方

| 表 | 持つもの |
| --- | --- |
| グループ | 名前、種類（本部・店舗）、Safe のアドレス、作成時の設定（オーナー・しきい値・ソルト）、配置日時 |
| メンバー | メールアドレス、名前、役職、所属するグループ、ロール、ダッシュボードのユーザーとパスキーへの紐づけ |
| パスキー | クレデンシャル ID、公開鍵（COSE 形式）、署名者のアドレス、署名者の配置日時 |
| 招待 | 種類（メンバー・パスキーの追加・パスワードの追加）、宛先、名前、役職、グループ、ロール、追加用リンクの対象のメンバー、期限、使用日時 |
| Safe の取引の提案 | 種類（出金・オーナーの変更・Safe の設定）、対象の Safe、取引の中身、Safe のノンス、取引のハッシュ、画面に出す内容（通貨・金額・宛先・対象のメンバー）、状態、作成者 |
| 提案への署名 | 対象の提案、署名したメンバー、署名者のアドレス、署名 |
| 入金 | 入金先の Safe とグループ、通貨、金額、送り元、取引のハッシュ、ブロックの日時 |
| 取り込みの記録 | チェーンから入金を取り込んだ最後のブロック |

出金・オーナーの変更・Roles v2 の設定は、どれも「Safe の取引にオーナーが署名し、中継用アカウントが送る」同じ流れのため、1つの表で扱います。署名の数・状態・ノンスの割り当てを種類ごとに作り分けずに済み、ダッシュボードの出金一覧にもまとめて並べられます。

入金は、bizzet のインデクサーが JPYC と USDC の送金のうちグループの Safe 宛てのものをチェーンから取り込み、取り込んだ最後のブロックを記録して次回はその続きから読みます。Safe のアドレスは設定を確定した時点で初めて bizzet の中に現れるため、それより前の入金を遡って取り込むことはしません。

パスキーの表はダッシュボードと同じ認証基盤（Better Auth）のパスキー用の拡張が作る表を使い、署名者のアドレスと配置日時の列を bizzet が足します。ダッシュボードのログインに使うユーザーとセッションの表も、この認証基盤のものです。

## デプロイの構造

<DeploymentDiagram />

- ホームチェーン（Sepolia）に、本部の Safe と店舗の Safe を置く
- 本部の Safe が上位にあり、各店舗の Safe の唯一のオーナーになる
- 本部の Safe はしきい値 2（2人承認）で、オーナーは3人以上。店舗の Safe のしきい値は 1
- 仮置き：ベータ版は Sepolia だけに配置する。客が払うほかのチェーンに置く Safe と Roles v2 は、自動ブリッジを有効にする時点で配置し、店舗ごとに置くかチェーンに1つにするかもそのときに決める

## 本部の Safe の数

本部の Safe は、1つの組織に1つだけ置きます。設計上は複数置くこともできますが、運用の負荷を下げるために1つに絞ります。

| 観点 | 1つに絞る理由 |
| --- | --- |
| 資金の把握 | 店舗の Safe から本部の Safe への一方向の流れだけ見れば、残高の確認・監査・会計との突合が済む |
| 自動ブリッジ | キーパーに許可する送り先が1アドレスで済み、店舗を増やしても Roles v2 の設定を変えずに済む |
| 承認の運用 | 2人承認のオーナーの顔ぶれとしきい値を1か所で管理でき、オーナーの交代もオンチェーンの操作1回で済む |
| 障害時の対応 | 鍵の紛失や復旧の手順が1パターンで済む |

本部の Safe が複数あると、店舗ごとに「どの本部へ送るか」の設定と確認が増え、設定漏れや誤送金の元になります。予算の枠を分けたいだけなら、本部の Safe を増やさず、店舗の Safe（グループ）を増やして対応します。別の法人や会計の単位で資金を完全に分けたい場合は、組織を分けて、組織ごとに本部の Safe を1つ置きます。仮置き：組織を分ける仕組み（ダッシュボードのログイン先・メンバー・権限の分離）は、複数の組織を扱う要件が出た時点で決めます。

## ロールの割り当て

| 役職 | 所属するグループ | ロール | オンチェーンでの姿 |
| --- | --- | --- | --- |
| 経営 | 本部 | Owner | 本部の Safe のオーナー |
| 会計部 | 本部 | Approver | 本部の Safe のオーナー |
| 店長 | 店舗 | Viewer | なし |
| スタッフ | 店舗 | Viewer | なし |

Owner と Approver は、パスキー署名者を所属するグループの Safe のオーナーとして加えます。Viewer はオンチェーンに何も持たず、パスキーはログインにだけ使います。

## メンバーの登録

メンバーは、Owner が発行した招待からだけ登録できます。招待はメンバーを1人作るためのもので、ダッシュボード（メールアドレスとパスワード）とウォレット（パスキー）のどちらで使っても、1回で使用済みになります。

### 招待

- Owner が、メールアドレス・所属するグループ・ロールを指定して発行する。有効期限は7日
- 登録済みのメールアドレスには発行できない。グループやロールの変更は招待ではなく、メンバー管理で行う
- 招待リンクはウォレットとダッシュボードのどちらでも開け、開いた側のログイン手段の登録が完了した時点でメンバーになる
- 登録の完了では、ログイン手段の保存・メンバーの作成・招待の使用済み化を1つのトランザクションで行い、使用済み化は未使用のときだけ成功する条件付きにする。同じ招待が同時に2回使われても片方だけが通り、途中で止まった登録は同じリンクから再開できる

### ログイン手段の追加

Owner と Approver は、ダッシュボードのパスワードと、Safe のオーナーになるためのパスキーの両方が要ります。招待で登録できるのは片方だけのため、もう一方はログイン済みの画面から発行した追加用のリンクで登録します。

- ダッシュボードにログイン中のメンバーは、ウォレット向けのリンクを発行し、スマートフォンで開いてパスキーを登録する
- ウォレットにログイン中のメンバーは、ダッシュボード向けのリンクを発行し、パスワードを設定する
- 追加用のリンクは発行した本人のメンバーにだけ紐づき、招待とは別の種類として扱う。有効期限は1時間

### パスキーの登録

パスキーの登録は WebAuthn の登録の手順に従い、端末から送られた値をそのまま信用せず、サーバーが内容を確かめます。

- サーバーがチャレンジを発行し、端末はそれを含めてパスキーを作る
- サーバーは登録の応答から、チャレンジと登録元のドメインが一致すること、公開鍵が P-256 であることを確かめる
- 公開鍵はサーバーが応答から取り出し、署名者のアドレスもサーバーが公開鍵から計算する。端末が送ったアドレスは使わない
- 同じ公開鍵か同じ署名者がすでに登録されていれば、登録を拒否する
- Owner と Approver の署名者は、登録の直後に中継用アカウントが配置する。Viewer の署名者は配置しない
- パスキーを紐づけるドメイン（rpId）はウォレットの本番のドメインとし、環境変数で固定する。あとから変えると登録済みのパスキーがすべて使えなくなるため、本番で最初のパスキーを登録する前に決める

## ウォレットのログイン

ウォレットのログインは、端末に保存した情報ではなく、バックエンドの対応表とサーバーでの署名の検証で行います。検証とセッションはダッシュボードと同じ認証基盤（Better Auth）のパスキー用の拡張が担い、内部では SimpleWebAuthn が WebAuthn の手順を処理します。

- サーバーがチャレンジを発行し、端末は登録済みのパスキーで署名する
- サーバーはクレデンシャル ID で対応表を引き、その公開鍵で署名を検証してからセッション（Cookie）を発行する
- 対応表にないパスキーではログインできず、この画面で新しいパスキーを作ることもしない。未登録の端末には、招待か追加用のリンクから登録するよう案内する

## Safe の作成

資金を置く Safe はグループの Safe だけで、メンバー個人の Safe は作りません。個人の Safe は、端末を失うと資金を動かせなくなるためです。

### 本部の Safe

- 本部の Owner と Approver を合わせて3人がパスキーを登録し終えた時点で、Owner がダッシュボードで、3人の署名者をオーナー、しきい値 2 とする設定を確定する。3人以上にするのは、1人がパスキーを失っても残る2人で入れ替えの承認ができるようにするため
- 確定した設定（オーナー・しきい値・ソルト）とアドレスをバックエンドに保存し、画面はこの値を使う
- 本部の Safe のオーナーはパスキーの署名者のため、ダッシュボード（メールアドレスとパスワード）では署名できない。設定の確定と出金の作成はダッシュボードでもできるが、署名はウォレットで行う
- 以後のオーナーの追加と削除（Owner や Approver の入れ替え、パスキーを失ったときの入れ替え）は、本部の Safe の取引として2人承認で行う。Safe を作り直すとアドレスが変わるため、作り直しはしない。オーナーが2人以下になる削除は行えない

### 店舗の Safe

- Owner がダッシュボードで店舗のグループを作った時点で、本部の Safe だけをオーナー、しきい値 1 として設定を確定し、アドレスを保存する
- 店舗の Safe の署名は本部の Safe がコントラクト署名（ERC-1271）で行うため、店舗の Safe からの出金と設定変更は本部の2人承認になる
- 店舗の Safe の最初の取引は Roles v2 の有効化で、店舗のグループを作った直後に本部の2人承認で行う。ロールはキーパーの送信元アドレスに与え、許可する呼び出しは JPYC と USDC の送金のうち宛先が本部の Safe のものだけにする。ホームチェーンの中の Sweep もこの仕組みで行う

### 配置のタイミング

- Safe のアドレスは確定した設定から決まるため、配置する前から入金を受けられる。店舗の Safe のオーナーに本部の Safe を指定することや、Roles v2 で送り先を本部の Safe に固定することも、アドレスだけで行えるため配置を待たない
- Safe の配置は、その Safe の最初の取引と同じ中継用アカウントの取引にまとめ、配置だけの取引は送らない。店舗の Safe の最初の取引に本部の Safe の署名が要るため、本部の Safe が未配置ならその中で先に配置する
- 配置を含む取引のガス代も、Paymaster が肩代わりする

## 出金の流れ

### 署名の対象

- メンバーが署名するのは Safe の取引（宛先・金額・データ・Safe のノンスを含む EIP-712 のハッシュ）で、ガス代や Paymaster の情報は含まない。そのため署名に期限はなく、2人目の署名まで何日空いても送れる
- 提案には作成した順に Safe のノンスを割り当てる。チェーン上のノンス以上で、送信前・送信済みの提案がまだ使っていない最小の番号を使う。先の提案が却下されて番号が空いた場合は、次に作る提案がその番号を埋めるため、後ろの提案は署名をやり直さずに、空いた番号の提案が実行されるのを待つ
- 署名がそろった提案は、中継用アカウントが `execTransaction` として送る。ガス代の見積もりと Paymaster の承認はこの時点で行う

### 出金の状態

| 状態 | 意味 |
| --- | --- |
| 申請中 | 提案はあるが、署名がまだない（店舗のメンバーの申請や、ダッシュボードで作った出金） |
| 承認待ち | 1人目が署名し、2人目を待っている |
| 送信済み | 2人分の署名がそろい、中継用アカウントが送った |
| 実行済み | ブロックに入り、Safe が実行した |
| 却下 | 申請者か Owner が実行前に取り下げた |

### 本部の出金

- Owner か Approver がウォレットで出金を作り、1人目として署名する。署名はバックエンドに保管する
- もう1人が同じ出金に署名した時点で、中継用アカウントが2つの署名を添えて送る

### 店舗の出金

- 店舗のメンバー（店長・スタッフ）は、ウォレットで返金などの出金を申請する。申請はバックエンドに保存し、オンチェーンには何も送らない
- 本部の Owner と Approver が申請を確認して署名し、2人分がそろった時点で店舗の Safe の取引として送る。店舗の Safe の署名は本部の Safe のコントラクト署名で、その中に2人のパスキーの署名を含める
- 仮置き：返金の件数が多い店舗向けに、店長へ上限付きの出金を委ねる仕組み（Roles v2 の許容量）は、ベータ版の利用状況を見て決める

## 強制する場所

| 項目 | 強制する場所 |
| --- | --- |
| 出金の承認 | Safe 本体（オーナーであることと、しきい値） |
| 2人承認 | 本部の Safe のしきい値 2 |
| 店舗からの出金 | 店舗の Safe の唯一のオーナーが本部の Safe であること |
| メンバーの追加（招待の発行） | バックエンド（Owner だけが発行できる） |
| Safe のオーナーの変更 | 本部の Safe のしきい値 2 |
| 残高の閲覧 | 画面側（オンチェーンでは強制しない） |
| Sweep の起動 | Roles v2（キーパーに、宛先を固定した関数だけを許可） |
| ガス代の肩代わり | Paymaster（中継用アカウントの取引だけを対象にする） |

権限管理の「権限の付与」は招待の発行を指し、Owner 1人で行えます。付与された Owner や Approver を本部の Safe のオーナーに加える操作はオンチェーンの設定変更にあたるため、2人承認で行います。

## 自動ブリッジとの接点

客が払うチェーンの Safe に着金した USDC は、Roles v2 のロールを持つキーパーが CCTP v2 の TokenMessenger を呼んで、ホームチェーンの本部の Safe へ移します。Roles v2 はキーパーに、受け取り先を本部の Safe に固定した呼び出しだけを許可するため、キーパーの鍵が漏れても資金はほかへ送れません。起動は、外部のサービスのキーパーが行います。
